===========
madmom-plus
===========

madmom-plus is a maintained fork of `CPJKU/madmom <https://github.com/CPJKU/madmom>`_, an audio signal processing library for music information retrieval (MIR). It keeps the upstream algorithms, public Python API, command-line programs, trained models, credits, and licences.

The distribution name is ``madmom-plus``. The import name remains ``madmom`` so existing applications and model pickle references keep working. Install one distribution per environment because ``madmom`` and ``madmom-plus`` provide the same Python package and executable names.

This development release, ``0.17.0.dev1``, updates isolated source builds for current Python, NumPy 2, Cython 3, and SciPy. It also fixes scalar online beat input, microphone byte decoding, integer resampling compatibility with current FFmpeg, and missing beat models in wheels. See `CHANGES.rst <CHANGES.rst>`_ for details and `docs/compatibility.rst <docs/compatibility.rst>`_ for tested versions and timings.

What madmom-plus improves over madmom
=====================================

The existing online Python processors now use one required C++ core for the supported frontend, float32 neural inference, forward DBN, and beat/peak kernels. The standalone engine uses the same arithmetic through a small `versioned C interface <native/include/madmom_engine.h>`_ with integer sample timestamps. Python names, arguments, command-line programs, model files, and musical defaults remain compatible. Custom operations without a native kernel retain their existing implementation.

On this AMD Ryzen 9 5900X host, the causal bulk Python path uses **0.04616 CPU seconds per audio second before integration and 0.01197 after integration: 3.86 times faster**. Frame-at-a-time processing improves from **0.06163 to 0.04574 CPU seconds per audio second: 1.35 times faster**. The streaming frontend alone improves from 0.01024 to 0.00858, a 1.19 times speedup. Peak process resident memory falls from **238.0 to 90.0 MiB** for the same 68.51 seconds of bulk audio; streaming peak memory stays near 80 MiB.

At the C API, the native frontend improves over the previous native implementation from 0.01101 to 0.00684 CPU seconds per audio second, a 1.61 times speedup. The native engine's live heap after a one-second push falls from 1,353,856 to 1,321,232 bytes; the short engine test shows no process peak-memory reduction.

The Python comparison uses the inherited Python/Cython path at commit ``3c7b36a`` with the same dependencies as the new core. Five paired trials alternate variant order on one pinned core, with one BLAS/OpenMP thread. CPU measurements exclude loading and initialization. NumPy remains faster for the standalone bulk frontend; complete-path gains also come from native neural inference and lower temporary storage. CPU frequency and other host work were not controlled, so these measurements describe this run. See `the full measurements and limits <docs/native.rst>`_, `paired trial data <docs/benchmarks/core-paired-host.json>`_, and `all stage measurements <docs/benchmarks/core-host.json>`_.

Compatibility is checked against stored outputs from unmodified madmom 0.16.1, not expected values generated by the new core. Across 687 public test frames, maximum absolute error is 2.39e-7 for frontend features and 4.48e-7 for Python-API activations; beat times match exactly on both recordings. The x86-64 installed wheel passes **1,100 tests and 165 subtests**. Tests retain upstream numerical limits and cover model edits, processor customization, reset, history transfer, serialization, and the restored single-frame time axis. All **92 packaged model files** remain unchanged. See `reference provenance and tolerances <docs/native-reference.rst>`_. These short examples establish compatibility, not general musical accuracy.

Maintenance also adds current Python/NumPy build support, complete model packaging, scoped legacy-pickle loading, corrected asymmetric beat-evaluation tolerances, worker cleanup, and FFmpeg-compatible integer resampling. Local Linux x86-64 and aarch64 wheels require glibc 2.38 or newer; ARM checks run under QEMU with both NumPy 1.26 and 2.4. Physical ARM performance, older manylinux targets, macOS, and Windows remain unverified. See `local wheel evidence <docs/native-wheels.rst>`_ and the `library scope <SCOPE.md>`_. Source builds now require a C++17 compiler.

Installation
============

Source installation uses PEP 517 build isolation. It installs Cython and NumPy build requirements automatically, then compiles the extension modules. A source checkout must include the pinned model submodule.

Requirements
------------

The package requires Python 3.9 or newer, NumPy 1.23.5 or newer at runtime, SciPy 1.13 or newer, and mido 1.2.6 or newer. The build environment requires setuptools 64 or newer, Cython 3 or newer, and NumPy 2 or newer. Source builds require C and C++17 compilers and matching Python development headers because the online Python processors use the required native core. On Debian or Ubuntu with the system Python, install ``build-essential``, ``python3-dev``, and ``python3-venv``.

Install ``ffmpeg`` for compressed audio input, resampling, and the full audio test suite. Optional packages are ``pyaudio`` for microphone input and ``pyfftw`` for FFT acceleration. The `aarch64 guide <docs/aarch64.rst>`_ gives 64-bit ARM Linux instructions and states what was verified under emulation.

Install from source
-------------------

Create a separate virtual environment so this distribution does not conflict with upstream madmom::

    git clone --recurse-submodules https://github.com/karimkfoure/madmom-plus.git
    cd madmom-plus
    python3 -m venv .venv
    . .venv/bin/activate
    python -m pip install --upgrade pip
    python -m pip install .
    python -c "import madmom; print(madmom.__version__)"

For an existing checkout, initialize the pinned model revision before installation::

    git submodule update --init --recursive

Use the source instructions until a ``madmom-plus`` release is published on PyPI. An upstream ``madmom`` release has different distribution metadata and does not include these maintenance changes.

Development and tests
---------------------

Install the package in editable mode with the test extra, then run all upstream tests::

    python -m pip install -e '.[test]'
    python -m pytest tests

To include documentation examples::

    python -m pytest --import-mode=importlib --doctest-modules madmom tests

Reinstall after changes to Cython extensions. To build a source archive and then build its wheel in an isolated environment::

    python -m pip install build
    python -m build

Upgrade a source checkout with ``git pull``, then run ``git submodule update --init --recursive`` and reinstall. Keep the pinned submodule revision unless you intend to validate new model data.

Package structure
-----------------

The package has a very simple structure, divided into the following folders:

`/bin <bin>`_
  this folder includes example programs (i.e. executable algorithms)
`/docs <docs>`_
  package documentation
`/madmom <madmom>`_
  the actual Python package
`/madmom/audio <madmom/audio>`_
  low level features (e.g. audio file handling, STFT)
`/madmom/evaluation <madmom/evaluation>`_
  evaluation code
`/madmom/features <madmom/features>`_
  higher level features (e.g. onsets, beats)
`/madmom/ml <madmom/ml>`_
  machine learning stuff (e.g. RNNs, HMMs)
`/madmom/models <https://github.com/CPJKU/madmom_models>`_
  pre-trained model/data files (see the License section)
`/madmom/utils <madmom/utils>`_
  misc stuff (e.g. MIDI and general file handling)
`/tests <tests>`_
  tests

Executable programs
-------------------

The package includes executable programs in the `/bin <bin>`_ folder.
If you installed the package, they were copied to a common place.

All scripts can be run in different modes: in ``single`` file mode to process
a single audio file and write the output to STDOUT or the given output file::

    DBNBeatTracker single [-o OUTFILE] INFILE

If multiple audio files should be processed, the scripts can also be run in
``batch`` mode to write the outputs to files with the given suffix::

    DBNBeatTracker batch [-o OUTPUT_DIR] [-s OUTPUT_SUFFIX] FILES

If no output directory is given, the program writes the output files to the
same location as the audio files.

Some programs can also be run in ``online`` mode, i.e. operate on live audio
signals. This requires `pyaudio <http://people.csail.mit.edu/hubert/pyaudio/>`_
to be installed::

    DBNBeatTracker online [-o OUTFILE] [INFILE]

The ``pickle`` mode can be used to store the used parameters to be able to
exactly reproduce experiments.

Please note that the program itself as well as the modes have help messages::

    DBNBeatTracker -h

    DBNBeatTracker single -h

    DBNBeatTracker batch -h

    DBNBeatTracker online -h

    DBNBeatTracker pickle -h

will give different help messages.
